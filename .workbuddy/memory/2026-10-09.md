## 六项布局修正（用户集中反馈：顶栏间隙/分段居中/切模式跳高/滚动条/通用页品字形）
1. **顶栏「播放中·随机」↔「壁纸来源」间隙过大**：两者原是 HStack 的**平级子项**（间距 10），
   而状态胶囊挂着 `.frame(maxWidth: 320)` —— maxWidth 会先吃掉一段可用宽度再排版，
   于是实际留白远大于设定值。修法：把两块收进同一个 `HStack(spacing: 6)` 的 trailing 组。
   **通则：带 maxWidth 的子项不要与兄弟平级，改放进定宽容器**。
2. **SlideSegmented 选中段文字没垂直居中**：白滑块走绝对 `offset(x)` 定位、段文字走 HStack 布局，
   两者在 `ZStack(alignment: .leading)` 里**垂直基准不同**（leading 只管水平）。
   修法：抽出 `let segHeight = geo.size.height - 4`，**两层都用它且都用 .frame 定位**。
   同时删掉段上的 `.frame(maxHeight: .infinity)`（与父层的定高 frame 冲突）。
3. **切到单循环窗体高度突变+ 冒出滚动条**：`rotationCard` 里那句说明是
   `if !rotationEnabled` **条件渲染**的 → 单循环时凭空多一行 → 内容变高 →
   `fitSettingsWindow` 把窗拉高 → 内容刚好越过阈值 → ScrollView 翻出滚动条。
   修法：**说明文字常驻、只换文案**（"按这个间隔自动换片。" ↔ "单循环时不换片…"），
   卡片高度恒定，切模式只剩颜色变化。
   ⚠️ 通则：**任何条件渲染的文案行都是窗体高度突变的来源**，优先改成常驻换文案。
4. **切页过程中闪滚动条**：ScrollView 默认 `.automatic` 在内容**刚好**等于视口高时就翻出指示器，
   而切页动画的中间帧反复越过阈值。修法 `.scrollIndicators(.hidden)` ——
   弃用 `.hidden` 的写法（那会让长队列页无法滚动）。
5. **通用页三卡品字形不对称**：「关于」卡有 58pt 图标 + 三行文字，是三张里唯一需要横向空间的，
   塞进半列必然被挤成两行，而另两张（开关型）只有一行 —— 怎么排都不对称。
   修法：**关于通栏置顶**，下面两卡并排（`VStack { aboutCard; TileGrid { autostart; appearance } }`）。
   两个开关的 identifier（autostart-toggle / glass-toggle）不变，UI 测试不受影响。

## 分段控件白块「看着没垂直居中」—— 是阴影不是布局（用户截图质疑）
拿用户截图**逐像素扫描**（自己写的 PNG 解码器 + 亮度扫描，见 /tmp/scan.py）才发现：
几何上白块与轨道中心**完全一致**（轨道 y25..47 中心 36；白块 y28..44 中心 36；
文字 y32..41 中心 36.5）—— 也就是说布局没问题。
真凶是 `.shadow(color: .black.opacity(0.10), radius: 2, **y: 1**)`：
向下偏移 1pt 把视觉重心拽下去了，于是看着「沉在下面」。
- 修法：y: 1 → **0**、radius 2 → **1.5**、opacity .10 → .13（对称阴影把「浮动」的读法
  补回来）。**修阴影而不是动 frame** —— 后者会真的错位。
- 复测（同方法）：上间隙 3px / 下间隙 1px → **4px / 4px**，完全对称。
- 同类修：`GlowSlider` 旋钮的 `y: dragging ? 2 : 1` → **y: 0**。
- **例外 `GlowToggle` 保留 y: 1**：旋钮是「压在轨道上」的语义，向下投影是接触感。
  判据不是「统一」，而是「这个阴影有没有语义」——无语义的偏移一律改 0。
⚠️ 方法论：**用户说「看着没居中」时先量像素再动手**。本次量出来是几何居中，
凭直觉去调 frame 反而会把它改坏。

## 品牌块偏上 + 侧栏菜单文字未对齐（同一根因：fixedSize 锁死垂直）
用户截图（90°旋转，`sips -r -90` 转正）量化：橙色图标中心 y=153.5，**红绿灯中心 y=224**
（红绿灯是系统画的、垂直居中于顶栏，可作基准）→ 品牌块**偏上约 70px@3x ≈ 23px，
换算到 44pt 顶栏就是偏了半格**。
- 根因：`.fixedSize(horizontal: true, **vertical: true**)` 把整块锁在自然高度 ——
  两行字（12pt + 9pt + 1pt 间距 ≈ 26pt）**高于**24pt 图标盒，于是图标被顶到文字块上沿。
  修法：改成 `.fixedSize(horizontal: true, **vertical: false**)`，垂直交给
  `.frame(height: topbarHeight)`。**有 frame 才有「在 44pt 里居中」这回事。**
- **侧栏导航行是同一根因**（用户一并指出）：`HStack(spacing: 10)` 没写 alignment，
  文字按自身16pt 行高贴在 28pt 图标盒上沿。修法：显式 `alignment: .center`
  + 文字补 `.frame(height: 28)`（与图标盒同高，基线才真落在中心）。
- 复测（ImageRenderer @4x + 自写 PNG 扫描）：图标偏差 **-0.50pt**、文字 **-0.38pt**，
  都在抗锯齿误差内；修复前是 -10pt 量级。
⚠️ **`.fixedSize` 的竖向版是「居中杀手」**：它只锁尺寸不锁位置，内容比容器矮/高时
上下就不对称。凡是要在固定高度容器里居中的视图，竖向一律不写 fixedSize。
（本轮与上一轮的SlideSegmented 阴影、这次的 fixedSize，是同一类问题的三个实例：
**「看着没居中」先量像素，再判断是几何错位还是视觉错觉**。）

## ⚠️ 本轮翻车复盘：连续 4 轮盲改（用户两次「没变化啊」）
**现象**：品牌块（壁纸儿 + 版本号）目视偏下，用户两次反馈「没变化」。

**我犯的错（按时间顺序）**：
1. **量错对象**。全程用截图坐标猜，但 `screencapture`/`osascript` 拿到的窗口位置
   一直在变（223,72,1024,570 → 0,0,1470,956），我按旧坐标裁剪/取像素，
   **有一次截到的是 WorkBuddy 自己的窗口、有一次是别的应用**。
   颜色判据也不严谨（品牌橙 #F4701B 满足 `r>190 and g<160 and b<150`，被误判成「红绿灯」）。
2. **基于错误结论盲改**。先后改了 4 版：加竖向 fixedSize → 删竖向 fixedSize →
   改 minHeight/maxHeight → 改 height 两步式。**每一版都基于我没验证过的测量**。
3. **ImageRenderer 误导**。用 ImageRenderer 对比 5 种 frame 写法，渲染**完全一致**
   （含「不加任何 frame」的裸版本）→ 得出「frame 写法对位置无影响」——
   这个结论本身没错，但它让我更加确信「问题不在 frame」，于是掉头去改结构，
   而真正的原因是 **hiddenTitleBar 的固有偏移**，从头到尾就没去查它。

**最终靠什么解决**：用户手动截图 + 我只量「分隔线 y=75」「红绿灯中心 y≈15.5」
「品牌图标中心 y≈53.5」「图标宽 23px=24pt（1x）」这几个**互相独立可交叉验证**的量，
才拼出真相：顶栏被撑到 75pt（=38 偏移 + 44 实际不够），品牌块比红绿灯低 38pt。
解法是显式补 `topbarContentTopInset = 38`，而不是继续跟 frame 较劲。

**教训（写死，别再犯）**：
- **量之前先确认对象**：`osascript` 拿窗口 position/size，拿不到就问用户，
  绝不用上一轮的旧坐标。截图后**先看一眼图**确认拍到了目标，再去取像素。
- **交叉验证**：单一指标（颜色判据、单一坐标）不可信。至少两个独立量互相印证
  （如「图标宽 23px ≈ 代码 24pt」确认缩放比，再算中心偏差）。
- **`hiddenTitleBar` 的固有偏移是既定事实**：红绿灯在标题栏层（中心 ≈15.5pt），
  SwiftUI 内容层从 y=0 起。产品要「与红绿灯同一行」就得显式补偏移，
  **别试图用 frame 让两层对齐** —— frame 只管内容自己，管不了另一层。
- **用户说「没变化」时，先停下重新确认测量链路**，不要接着改。
