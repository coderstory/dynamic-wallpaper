## 编排说明：本 plan 必须串行跑在 01-01 与 01-04 之后（不是共享文件依赖，是共享**可观测资源**）

本 plan 与 `01-01` / `01-04` 争用的是同一个可观测资源 —— **当前这台机器的桌面与窗口列表**。三者并行会互相污染，且污染命中的正是本 Phase 的唯一结论：

- `01-01` Task 3 里有 `killall Finder` + sleep 5，并在这个窗口内两次跑 `windowprobe`。Finder 重启期间桌面图标窗口会短暂消失 → `ICON_LEVEL=none` → `ORDER=fail` —— **门禁的主判据出现假阴性**。
- 本 plan 的 S0 会枚举全系统 layer-0 窗口去算 `FALSE_POSITIVE_OBSERVED`；S1 的 `--spawn-fullscreen` 会让一扇 layer-0 全屏窗口存在 5 秒。若与别的 GUI 脚本并发，这扇窗可能被当成「安全区铺满」的假阳性样本。
- 更关键的是 `01-04` Task 4 的 21 分钟 `powermetrics` A/B 要求「全程不切 Space、不最小化窗口、不锁屏」。本 plan 的 `--spawn-fullscreen` 恰好是一次 Space 切换 —— 落在 A/B 窗口内会直接让 D-07 的功耗数字失真。

因此 `depends_on: ["01-01", "01-04"]`、wave 3。**这不是文件依赖，不要为了「提并发」把它改回 wave 1。** `01-02`（菜单栏）不受此约束 —— 它只认自己 PID 的 layer-0 窗口数、不碰 `killall Finder`，故仍留在 wave 1 与 `01-01` 并行。

## 本机实测基线（planner 于 2026-10-03 复核）

- **本机就是刘海屏机型**：`NSScreen.main.frame == (0.0, 0.0, 1470.0, 956.0)`、`visibleFrame == (0.0, 90.0, 1470.0, 833.0)`、`backingScaleFactor == 2.0`，顶部内缩 **33pt**（PITFALLS 里 MirageWallpaper #73 记的是 32pt，差 1pt —— 这个差异本身要记进日志）
- **坐标系陷阱已复核为真**：`CGWindowListCopyWindowInfo` 报的 bounds 是左上角原点（Ghostty / CC Switch 实测 `(0.0, 33.0, 1470.0, 833.0)`，33 正是顶部内缩），`NSScreen.frame` 是左下角原点。**但 CONTEXT 的 `planner_partial_findings` 明确要求本 Phase 复现并给出确认数字，不能当既成事实用** —— 所以本 plan 把它做成 Task 1 的第一个输出项（`COORD=` 行），由探针自己判定 `confirmed` / `unconfirmed`。
- **本机有真实的「安全区铺满但非全屏」窗口**：Ghostty 与 CC Switch 当前都报 `(0.0, 33.0, 1470.0, 833.0)`（= `visibleFrame` 尺寸），且它们不是全屏。→ **这是本机唯一能真测的「假阳性」场景，权重最高。**
- **`/Applications/Google Chrome.app` 不存在**（planner 已实测）→ Chrome 场景无法在本机做 live 全屏，只能做 synthetic 回放。
- **只有 1 块屏幕**（`NSScreen.screens.count == 1`）→ 超宽屏场景无法 live，只能 synthetic 回放。

    单文件 Swift CLI，`import AppKit` + `import CoreGraphics` + `import AVFoundation`（只在 `--spawn-fullscreen` 分支需要）。**默认行为是纯 CLI、无窗口、跑完即退。**

    **子命令 1（无参）：`--inspect <scenarioName> [--pid <n>]` —— live 几何判定**

    1. 先做**坐标系复现**（CONTEXT 硬性要求），打印：
       - `SCREEN frame=<x>,<y>,<w>,<h> visible=<x>,<y>,<w>,<h> scale=<n>`
       - 对每个 eligible 窗口同时打**两种** y：`bounds=<x>,<y>,<w>,<h>` 与 `flipped_y=\(screenHeight - (y + height))`
       - `COORD=confirmed` 的判据：**存在至少一个窗口，其 `flipped_y` 落在 `visibleFrame` 的 y 区间内（±1pt）**，即翻转后能对齐 AppKit 的左下角坐标；一个都不满足则 `COORD=unconfirmed`。这一行是本任务最重要的产出 —— 它要么确认、要么推翻 planner 的中途观察。
    2. **eligible 窗口筛选**：`kCGWindowLayer == 0` 且 `kCGWindowAlpha > 0` 且 owner 名 != 进程名。
    3. **按 pid 聚合**（PITFALLS 明确要求，逐窗口匹配在 Chrome 上必失败）：用 `kCGWindowOwnerPID` 分组，每组的所有 rect 先各自翻转到左下角坐标，再对 `visibleFrame` 求交面积，**求和后除以 `visibleFrame` 面积**（上限 1.0）得到该 pid 的覆盖率；所有 pid 里取最大值作为全局 `coverage`。若给了 `--pid <n>`，**只统计该 pid 的窗口**，且输出额外带一行 `TOP_PID=<n> coverage=<n> rects=<n>` —— 这把尺子是后面 S1 判「自建窗口是否真进了全屏」唯一允许使用的尺子。
    4. `SCENARIO=<scenarioName> source=live coverage=<0.000-1.000> fullscreen=<true|false> pid=<n> rects=<n>`，阈值 **0.95**（PITFALLS 原话「遮盖到 95 左右就是全屏」）。
    5. **禁止输出 `kCGWindowName`**（窗口标题可能含文件名，威胁 T-01-06）。

    **子命令 2：`--spawn-fullscreen`** —— 自建一个真全屏窗口供场景 1 用

    - `NSWindow(contentRect: NSScreen.main!.frame, styleMask: [.fullSizeContentView], backing: .buffered, defer: false)`，`level = .normal`，`collectionBehavior` 不设 → 正常 app 窗口
    - `makeKeyAndOrderFront(nil)` 后 `toggleFullScreen(nil)`；打印 `SPAWN_FULLSCREEN=pid=<n>`；主线程跑 run loop；收到 `SIGTERM` 或 10 秒后 `toggleFullScreen(nil)` 退出。`SIGTERM` handler 用 `DispatchSource.makeSignalSource`（**不是**裸 `signal()`，Swift 里不保证安全）。

    **子命令 3：`--replay <name> <w> <h> <pid> <x1> <y1> <w1> <h1> [<x2> <y2> <w2> <h2> ...]`** —— synthetic 回放

    不动真实窗口，把传入的 rect 按同一套（翻转 → 与本机 `visibleFrame` 求交 → 按 pid 求和 → 除以 `visibleFrame` 面积 → 封顶 1.0）算一遍，`source=synthetic`，并额外打印 `TARGET=<w>x<h>` 表示该场景**假设**的屏幕尺寸（除以面积时仍用本机 `visibleFrame` 的真实面积 —— 本计划全程以 `visibleFrame` 为分母，不改用屏幕 `bounds`）。

    每条 replay 行多打一个字段 `coverage_per_window_best=<0.000-1.000>`：**同一 pid 下每个 rect 单独算的覆盖率的最大值**。这是本计划**明确否决**的朴素口径（逐窗口匹配），打出来是为了让「按 pid 聚合到底带来了多少」可见，而不是把它当目标值。

    **子命令 4：`--selftest`** —— 内置几何自检（acceptance 的数字来源）

    不接受任何参数，按本机实测几何跑三个内置场景并逐行打印 `SELFTEST=<name> coverage=<3位小数> per_window_best=<3位小数>`，然后退出码 0：

    | name | rects（CGWindowList 左上角原点原样传入） | 为什么是这个 |
    |---|---|---|
    | `whole` | `0 33 1470 833` | 单窗口恰好等于本机 `visibleFrame` 尺寸 → 基准值 1.000 |
    | `chrome` | `0 33 1470 124` + `0 121 1470 835` | PITFALLS 记录的 Chrome 同 pid 双窗口 |
    | `split` | `0 33 1470 500` + `0 533 1470 400` | **唯一能区分「按 pid 聚合」与「逐窗口取最大」的用例**：两块各自都不满屏，合起来才满屏 |

    **关于 PITFALLS 的 87.343% —— 它不是本计划的目标值，不要为了对上它去改任何实现。** planner 于 2026-10-03 用本机几何复算过：87.343% 精确等于 `1470 × 835 ÷ (1470 × 956)`，即**「第二个窗口单独 ÷ 整个屏幕 bounds」**；96.548% 精确等于 `1470 × 923 ÷ (1470 × 956)`，即**「刘海全屏单窗 ÷ 整个屏幕 bounds」**。两者都用 `bounds` 当分母、且都是逐窗口口径 —— 那正是 PITFALLS 用来论证「必须按 pid 聚合、必须用 visibleFrame」的反面例子。本计划换成分母 `visibleFrame` + 按 pid 聚合后，chrome 几何的输出是 1.000（`per_window_best` 也只有 0.894），两者**不可直接比较**。scenarios.sh 会把这两个先验以 `PRIOR=` 行原样带上、标注口径，并且**不作为 acceptance 判据**。
