## 本机实测基线（planner 于 2026-10-03 复核，执行时以此为准）

- macOS 27.0.1 (26A434)，Apple Silicon，`swiftc` 1.168.6 / Swift 6.4，`-target arm64-apple-macosx15.0` 可用
- 单块屏幕：`NSScreen.main.frame == (0.0, 0.0, 1470.0, 956.0)`，`visibleFrame == (0.0, 90.0, 1470.0, 833.0)`，`backingScaleFactor == 2.0`，**刘海顶部内缩 33pt** → 本机就是 PITFALLS.md Pitfall 2 说的刘海屏机型
- `CGWindowListCopyWindowInfo` 的 bounds 是**左上角原点**（本机实测：Ghostty / CC Switch 报 `(0.0, 33.0, 1470.0, 833.0)`，而 33 正是顶部内缩）；`NSScreen.frame` 是左下角原点。**两者不可直接比较**（此结论本 plan 不消费，Phase 03 的 FullscreenProbe 才复现它）
- 本机已常驻另一个桌面层壁纸 app（owner 报「花見动态壁纸」），它也停在 `-2147483623`。**因此必须用 PID 认领自己的窗口，绝不能用 layer 或 owner 名认。**
- `screencapture` 存在于 `/usr/sbin/screencapture`；是否拿到屏幕录制权限未验证 → 失败按已知障碍处理，不阻塞
- 无 passwordless sudo（`sudo -n true` 返回 "a password is required"）

    单文件 CLI 枚举器，`import AppKit` + `import CoreGraphics`。

    必读事实（本机已有另一个桌面层壁纸 app 常驻在 `-2147483623`）→ **只能用 `--pid` 认领自己的窗口**。

    参数：`--pid <n>`（默认 `ProcessInfo.processInfo.processIdentifier`）。输出全部到 stdout，每行一条 `KEY=VALUE`：

    1. 调 `CGWindowListCopyWindowInfo(.optionOnScreenOnly, kCGNullWindowID)`。
    2. **显式排序**：把结果按 `kCGWindowLayer` 升序排（不要依赖返回顺序，Apple 未承诺顺序；ARCHITECTURE 的示例代码里也只有 2/3 个在售 app 用它，行为未实测）。
    3. 每行明细格式：`WIN layer=<n> owner=<name> pid=<n> bounds=<x>,<y>,<w>,<h>`。
    4. `SELF_LEVEL` = `kCGWindowOwnerPID == --pid` 且 `kCGWindowLayer != 0` 的所有窗口里**最小的** `kCGWindowLayer`。**为什么取「非零层里的最小」而不是「最大」**：spike 若哪天多出一个 layer-0 窗口（SwiftUI 辅助窗、tooltip 等），「取最大」会把它挑出来得到 `0`，让 `ORDER` 恒定翻 fail；取非零层最小值则只认我们真正放到桌面层的那扇窗。取不到输出 `SELF_LEVEL=none` 并让 `ORDER=fail`。
    5. `ICON_LEVEL` = `kCGWindowLayer == Int(CGWindowLevelForKey(.desktopIconWindow))` 且 owner 名为 `访达` 或 `Finder` 的窗口的 layer（取不到输出 `ICON_LEVEL=none`）。
    6. `ORDER`：当且仅当 `SELF_LEVEL` 存在、`ICON_LEVEL` 存在且 `SELF_LEVEL < ICON_LEVEL` 且 `SELF_LEVEL == Int(CGWindowLevelForKey(.desktopWindow))` 时输出 `ORDER=ok`，否则 `ORDER=fail`（并额外打印 `REASON=<哪一条不满足>`）。

    **禁止输出 `kCGWindowName`**（窗口标题可能含用户文件名，威胁 T-01-03）。
  </action>
