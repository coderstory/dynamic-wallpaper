    **`Sources/PicCore/Playback/FrameDriver.swift`（新建）** —— 把 Phase 1 的 `FrameTicker` 降级逻辑搬进产品，**写法照抄，逻辑不改进**：
    - `attach(to screen: NSScreen)` 里 `screen.displayLink(target:selector:)` + `preferredFrameRateRange` + `add(to: .main, forMode: .common)`
    - 1.0 秒后若 tick 数为 0 → 打一行 `REFRESH_DRIVER=timer_fallback_hz30` 并起 30Hz `Timer`（加到 `RunLoop.main` 的 `.common` mode）
    - 收到 tick 时打一行 `REFRESH_DRIVER=display_link`（**只打一次**，不刷屏）
    - **`invalidate()` 与 `Timer` 的 `invalidate()` 在同一处**（D-14 / Pitfall 4 的 observer 配对纪律；Pitfall 16 提到 `teardownGrace = 15s` 会让旧 renderer 长时间存活 —— 本 Phase 只做窗口生命周期，**不引入 15 秒宽限期**）

    **本 Phase 的 `FrameDriver` 干什么用？** 它**不驱动播放** —— `AVPlayer` 自己按视频的时间戳出帧，壁纸播放根本不依赖显示刷新。这里的问题是 Phase 1 把帧号当「画面在动」的证据写进了产品级代码。正确处置：`FrameDriver` 在产品里**只用于测量，不用于渲染**（不打帧号到屏幕上，只统计 tick 率并写一行 `REFRESH_TICK_RATE=<n>`）。**不要**把它接进任何渲染路径。

    **它唯一的引用点是 `AppDelegate`** —— `AppDelegate` 建一个 `FrameDriver`、`attach(to: NSScreen.main)`、启动后由它自己打 `REFRESH_DRIVER=` / `REFRESH_TICK_RATE=`。全树**只允许这两处**出现 `FrameDriver` 这个名字（类型声明处 + AppDelegate 的使用处），不许有第三处。这条「只允许两处」是可判定形式（`grep -rl` 后排除这两个文件应为空），比「同时为 0 或同时非 0」那种两处计数的相互约束可靠得多。

    **`scripts/run-probe.sh refresh` 子命令** —— 分别在 `swift run` 产物与 `build/Pic.app` 产物下各跑一次，写 `evidence/refresh.log`：
    ```
    REFRESH_RUN_MODE=swift_run   DRIVER=<display_link|timer_fallback_hz30>  TICK_RATE=<n>
    REFRESH_RUN_MODE=app_bundle  DRIVER=<display_link|timer_fallback_hz30>  TICK_RATE=<n>
    ```
    `TICK_RATE` 是 10 秒窗口内实测 tick 数 ÷ 10（不是估计值）。

    **结论分三种，逐字写进 log，不许模糊：**
