## 🔴 P0 · 必修

### P0-1 单循环模式下，每到一个轮换间隔视频就从头重播

- 位置：`Sources/PicCore/Playback/RotationController.swift:175-198`（`advance`）+ `Playback/Router` 装载链
- 级别：🔴 Critical（用户可见的核心功能损坏，且是默认路径）

**现象**：默认是 `.loopSingle` + 300 秒间隔。每 5 分钟壁纸会跳回第 0 秒重新开始。

**根因**：`start()` 无条件调 `reschedule()`；定时器到点 → `rotationElapsed()` → `advance(.rotationElapsed)`。`.loopSingle` 分支算出 `nextIndex = 0`，而 `currentIndex` 本来就是 0，于是照常执行 `onAdvance?(items[0])`。这条回调的唯一实现是 `PlayerLoadingAdapter.loadPlayback(url:)` → `player.load(url:)`，它新建 `AVPlayerItem`、清空队列、重建 `AVPlayerLooper`——**播放头归零**。

`AVPlayerLooper` 本来就在无缝循环，这一路装载纯属多余且有害。测试 `RotationControllerTests.testRotationElapsedHoldsLoopSingleLocked`（:263）锁的是「`currentIndex` 锁死在同一条」，锁的是索引，不是「不许重新装载」——所以测试全绿但行为是错的。这正是「判据锁住了错误的量」的典型。

```swift
// Sources/PicCore/Playback/RotationController.swift
private func advance(reason: AdvanceReason) {
    guard !items.isEmpty else { return }
    let previousIndex = currentIndex          // ← 新增
    let nextIndex: Int
    switch mode { /* 三个 case 不变 */ }

    currentIndex = nextIndex
    advances.append(RotationAdvance(reason: reason, index: nextIndex))

    // 到点解析出的下标与切换前相同 → 记一次切换，但不重新装载。
    // onAdvance 的下游是 player.load(url:)，它会重建 AVPlayerItem 与 looper、
    // 把播放头归零；单循环下这就等于「每到一个间隔从头重播一次」。
    // 循环本身由 AVPlayerLooper 负责，不需要靠重新装载维持。
    guard !(nextIndex == previousIndex && reason == .rotationElapsed) else {
        reschedule()
        return
    }
    onAdvance?(items[nextIndex])
    reschedule()
}
```

为什么这样改是对的：保留了「索引锁死」与 `advances` 打点（原测试仍绿），只砍掉那次有害装载。`loopList` 只有 1 条、`.shuffle` 洗牌袋边界撞回同一个下标时同样受益。

### P0-2 设置窗「选择…」换了目录，播放的还是旧目录

- 位置：`Sources/PicApp/AppDelegate.swift:509-513`（`requestFolderNow`）+ `Sources/PicCore/Media/MediaLibrary.swift:49-52`（`scan`）
- 级别：🔴 Critical（核心按钮看起来是坏的）

**现象**：选完新目录，视频数量不变、壁纸不换。只有再点「重新扫描」才生效。

**根因**：`MediaLibrary.scan(folder:useCache:)` 的缓存**不按目录 key**——`if useCache, let cached { return cached }`，只要缓存非空就返回，完全不看 `folder` 是不是同一个。而 `requestFolderNow()` 是唯一没有调 `library.invalidateCache()` 的重扫入口（对比 :630 `rescanLibrary()` 就调了）。

正确做法是**让缓存自己认目录**，而不是指望每个调用方记得失效——后者迟早再漏一个：

```swift
// Sources/PicCore/Media/MediaLibrary.swift
private var cached: MediaLibraryReport?
private var cachedRootPath: String?          // ← 新增

public func scan(folder: URL, useCache: Bool = true) async throws -> MediaLibraryReport {
    let key = folder.standardizedFileURL.path
    if useCache, let cached, cachedRootPath == key { return cached }   // ← 目录也参与判据
    // ... 原逻辑不变 ...
    cached = report
    cachedRootPath = key                     // ← 新增
    scanCount += 1
    return report
}

public func invalidateCache() {
    cached = nil
    cachedRootPath = nil                     // ← 新增
}
```

顺手补上另一道（`AppDelegate.requestFolderNow`）：`if await pickFolder() == .accepted { library.invalidateCache(); await rescanAndApply() }`。

## 🟠 P1 · 本期迭代内修

### P1-1 转码页每次切回，已完成的条目全部变成「失败 · name_collision」

- 位置：`Sources/PicApp/Transcode/TranscodeSection.swift:78-82`（`onAppear`）+ `Sources/PicCore/Transcode/TranscodeQueue.swift:100-126`（`enqueue`）
- 级别：🟠 Major

**现象**：转完一批后切走再切回「转码」TAB，每个已完成/已跳过的源文件都会多出一行「失败 · name_collision」。切 N 次多 N 组。

**根因**：`enqueue` 的去重只看 `isActive`（pending/running），「已终态的同路径允许再入队」。而 `onAppear` 每次都调 `loadCandidates()`，把同一批源再入队一次；新 job 的产物路径与已终态 job 的产物路径相同 → 撞 `claimedOutputs` → 标 `name_collision`。`claimedOutputs` 是从**全部** job 收集的，等于用历史记录去判失败。

修在调用侧最干净（`loadCandidates` 的语义本就是「补新文件」，不是「重建清单」）：

```swift
// Sources/PicApp/Transcode/TranscodeViewModel.swift
func loadCandidates() {
    guard let root = wallpaperRootProvider() else { return }
    let known = Set(queue.jobs.map { $0.sourceURL.path })
    let fresh = TranscodeCandidateFilter.candidates(in: root)
        .filter { !known.contains($0.path) }
    queue.enqueue(sources: fresh, deletesSource: false)
    reload()
}
```

同时把 `TranscodeQueue.enqueue` 的 `claimedOutputs` 收窄到活跃 job（`jobs.filter { Self.isActive($0.state) }`）——已终态 job 的产物占位不该参与碰撞判定，否则「失败后修好文件再转一次」这条重试路径也被堵死。

### P1-2 转码列表没有滚动容器也没有高度上限

- 位置：`Sources/PicApp/Transcode/TranscodeSection.swift:24-31`
- 级别：🟠 Major（列表一长窗口就废）

`ForEach` 直接铺在 `CompactCard` 里，既没有 `ScrollView` 也没有 `LazyVStack` 和 `maxHeight`。同文件的降帧列表（`FpsTranscodeSection.swift:88-98`）是 `ScrollView + LazyVStack + frame(maxHeight: 220)`——同一个窗口里两种写法，转码那份会随 job 数线性撑高窗口，几百个 MKV 时窗口直接长到屏幕外。照抄降帧那份即可。

### P1-3 锁屏通知在任意线程回调，却在里面断言 MainActor

- 位置：`Sources/PicCore/System/LockWatcher.swift:51-60`
- 级别：🟠 Major（可能崩溃 / 数据竞争）

```swift
center.addObserver(forName:..., object: nil, queue: nil) { _ in
    MainActor.assumeIsolated { onChange(self.currentLockState()) }   // queue: nil = 投递线程
}
```

`queue: nil` 表示 block 在**投递方线程**执行。`DistributedNotificationCenter` 不承诺主线程。同仓的 `DisplayWatcher`（:114 `queue: .main`）和 `FullscreenDetector`（:126 `queue: .main`）都显式写了 `.main`，只有这里漏了。

```swift
center.addObserver(forName: Notification.Name(names.locked), object: nil, queue: .main) { _ in
    MainActor.assumeIsolated { onChange(self.currentLockState()) }
}
```

`assumeIsolated` 是把「我保证在主线程」这个断言交给编译器，猜错了就是未定义行为——这不是「大概没事」，是必须给对的前提。

### P1-4 降帧点「取消」后，下一次「开始降帧」会空转一次

- 位置：`Sources/PicCore/Transcode/FpsTranscodeQueue.swift:245-262`
- 级别：🟠 Major（用户点了没反应）

**根因**：`consumeCancel()` 只在 `while` 循环体里被调用。如果被取消的是**最后一个** pending job，`runJob` 返回后 `jobs.firstIndex(where: .pending)` 为 nil → 直接 `break`，`_cancelRequested` 永远停在 true。下次 `run()` 第一轮就被 `shouldStop()` 挡掉并消费掉标志，用户看到「点了开始，什么都没发生」，再点一次才动。

```swift
public func run() async {
    guard !isRunning else { return }
    isRunning = true
    defer { isRunning = false }
    var didWork = false
    while true {
        guard let index = jobs.firstIndex(where: { $0.state == .pending }) else {
            // 排空退出也必须清一次取消标志：留着它会让下一次 run() 的第一轮
            // 被陈旧标志直接挡掉，表现是「点了开始没反应」。
            _ = consumeCancel()
            break
        }
        if shouldStop() {
            if consumeCancel() { jobs[index].state = .pending; onJobsChanged?() }
            break
        }
        await runJob(at: index)
        didWork = true
    }
    if didWork { onBatchFinished?() }
}
```

### P1-5 转码成功后无条件删源，且产物名扁平、跨批次会互相覆盖

- 位置：`Sources/PicCore/Transcode/TranscodeQueue.swift:209-230` + `Transcode/TranscodeOutputNaming.swift:32-40`
- 级别：🟠 Major（不可恢复的素材丢失路径）

两条叠加起来才致命：

1. **产物名是扁平的** `Converted/<stem>.mp4`。`a/clip.mkv` 与 `b/clip.mkv` 算到同一个产物路径。批次内的碰撞有 `name_collision` 挡着，但**跨批次没有**——第二批会 `removeItem(outputURL)` 静默覆盖第一批的产物（第一批的源已经被删了）。
2. **删源只认退出码 0**，完全不校验产物。ffmpeg 退出 0 但产出 0 字节/无视频轨的情况（磁盘写满、`-map` 落空）会照删源。

立刻可做的止血（删源前校验产物）：

```swift
// Sources/PicCore/Transcode/TranscodeQueue.swift，替换 :228-230
if jobs[index].state == .succeeded, jobs[index].deletesSource {
    if Self.looksLikeUsableOutput(outputURL) {
        try? trashProvider(source)
    } else {
        // 退出码 0 但产物不可用 —— 绝不删源。留着源，下一轮 skipDecision 会幂等跳过。
        jobs[index].state = .failed(reason: "output_unverified")
    }
}

/// 退出码不是「产物可用」的充分条件：磁盘写满、map 落空都会退出 0 但产出空文件。
/// 只做能同步做完的检查（体积 > 0），不做 AVAsset 探测 —— 那是 async，会把状态机拖长。
private static func looksLikeUsableOutput(_ url: URL) -> Bool {
    guard let size = (try? FileManager.default.attributesOfItem(atPath: url.path))?[.size] as? Int64 else {
        return false
    }
    return size > 0
}
```

根本修法是**把产物目录做成镜像子目录** `Converted/<源相对路径>/<stem>.mp4`，从根上消掉同名碰撞。改动面要一起带上的三个耦合点：`TranscodeOutputNaming.outputURL` / `temporaryURL`、`FpsDownscaleCommand.derivativeName`、`PlaybackPool.derivativeByName`（它靠 `lastPathComponent` 认回关系，改成镜像后要改判据）。这需要一份老 `Converted/` 的迁移，单独立项。

## 🟡 P2 · 性能与可维护性

### P2-1 播放池合并是 O(n²)

- 位置：`Sources/PicCore/Transcode/PlaybackPool.swift:8-70`

`liveDerivative` 对**每个** root 条目做 `converted.first(where:)`（:42、:53），`isOrphanDerivative` 对**每个** converted 条目做 `table.entries.contains`（:67）。1000 条素材 × 1000 个产物 = 100 万次路径字符串比较，而且这段代码在**每次重扫**（改个设置、转完一批、菜单点重扫）都跑一遍。

改成字典一次建好：

```swift
public static func build(root: [VideoItem], converted: [VideoItem],
                         table: FrameRateTable) -> [VideoItem] {
    let byPath = Dictionary(converted.map { ($0.url.path, $0) }, uniquingKeysWith: { a, _ in a })
    let byName = Dictionary(converted.map { ($0.url.lastPathComponent, $0) },
                            uniquingKeysWith: { a, _ in a })
    // 源已不在 root 里的产物 = 孤儿，一次性算好，不逐条扫表。
    let liveRootPaths = Set(root.map(\.url.path))
    let orphanDerivativePaths = Set(table.entries.compactMap { entry in
        liveRootPaths.contains(entry.sourcePath) ? nil : entry.derivativePath
    })

    var pool = root.map { item in
        liveDerivative(for: item.url, byPath: byPath, byName: byName, table: table) ?? item
    }
    var seen = Set(pool.map(\.url.path))
    for item in converted where !seen.contains(item.url.path) {
        if orphanDerivativePaths.contains(item.url.path) { continue }
        seen.insert(item.url.path)
        pool.append(item)
    }
    return pool
}
```

`liveDerivative` / `derivativeByName` 的签名跟着换成查字典（原语义与两条判据顺序不变）。

### P2-2 帧率表每探一个文件就全量落盘一次

- 位置：`Sources/PicCore/Transcode/FpsTranscodeQueue.swift:221` → `FrameRateTable.upsert`（:105-112）

`upsert` 内部 `try save(to:)`，而 `save` 是「建目录 + JSONEncoder 全量编码 + `.atomic` 写入（临时文件 + rename）」。500 个新文件 = 500 次全表编码 + 500 次原子写盘。同理 `writeTableState`（:329-332）每个 job 都要 `load` 一遍再 `save` 一遍。

改法：`FrameRateTable` 加一个不落盘的变更口（`upsertInMemory` / `updateStateInMemory`），由 `scan()` 在循环结束后 `save` 一次；`writeTableState` 每个 job 一次全量写可以接受（job 粒度本来就是状态跃迁），但把 `load` 提到批次外、复用同一个 `table` 实例更省。

### P2-3 降帧 TAB 每次出现都全量重扫整个片库

- 位置：`Sources/PicApp/Transcode/FpsTranscodeSection.swift:191-194`

`onAppear` 里调 `viewModel.scan()`，每次切回这个 TAB 就重新枚举壁纸目录 + 对每个文件开一次 `AVURLAsset` 探帧率，而且整段跑在 `@MainActor` 上（`await` 之间仍占主线程）。`scan()` 的结果已经在 `FrameRateTable` 里增量了，但 UI 侧没有「本次会话已扫过」的门。

最小改动：在 `FpsTranscodeViewModel` 里记一个 `hasScannedInThisSession`，`scan()` 首次必须跑、之后只在用户显式点「重新扫描」时跑。

### P2-4 每打一行日志就开关一次证据文件

- 位置：`Sources/PicCore/Render/WallpaperWindowController.swift:80-90`

`mirror` 每次都 `FileHandle(forWritingTo:)` → `seekToEnd` → `write` → `close`。`tick()` 每 2 秒一行、每次 hold 跃迁多行、拖一次滑杆几十行。改成持有长驻句柄（`static` + 锁），进程退出时 `close`。

### P2-5 release 二进制里 2 秒定时器在空转

- 位置：`Sources/PicApp/AppDelegate.swift:406-421`

`emit` 被 `#if !PIC_NO_PROBE` 包着，但 `startObservability()` 和 `tick()` 本身没有——交付版每 2 秒照样读一次 `player.currentTime()` 然后丢掉。整个 `startObservability` / `tick` 一起放进 `#if !PIC_NO_PROBE`。

### P2-6 其他

- `RotationController.advances` 无上限增长（:195），每 5 分钟一条；退出时只用它打个计数（AppDelegate:360）。改成只留计数或一个环形缓冲。
- `MediaLibrary.lastError`（:32、:77、:86）写了从不读——死状态。
- 常量重复：`Metrics.windowWidth = 780` 与 `SettingsPresentation.windowWidth = 780` 两份；速度滑杆的 `range: 0.5...2`（SettingsView:104）与 `SettingsPresentation.rateBounds` 两份。后者正是本仓自己写的「窗口常量是唯一来源」要防的事。
- `MediaLibrary.scan` 对每个通过扩展名的文件调 `resolvingSymlinksInPath().standardizedFileURL.path`（:125），每个文件一轮路径解析。此处 `values.isSymbolicLink != true` 已经成立，是纵深冗余但成本实打实。

- `runJob(at index:)` 在两个队列里都用下标跨 `await` 访问 `jobs`。目前 `scan()`/`enqueue()` 的时序让它是安全的，但改成按 `job.id` 取更抗改。

## 🔵 P3 · 边界与体验

- **壁纸窗口不随分辨率/换屏重建**：`WallpaperWindow.init` 用 attach 那一刻的 `screen.frame` 定死（WallpaperWindow.swift:22）。`DisplayWatcher` 的重配置回调只喂仲裁器，不碰窗口；`reassert()` 只重设 `collectionBehavior`。换外接屏或改分辨率后壁纸尺寸不对。重配置回调里比对 `NSScreen.main.frame` 与 `window.frame`，不一致就 `setFrame(_:display:)`。
- **`ExternalToolLocator` 的 `which` 兜底没再校验**（:43-46）：显式路径都过了 `isExecutableFile`，`which` 给的路径直接采信。GUI app 的 PATH 通常很短，风险不高，但两个来源用同一道闸才一致。
- **`FullscreenDetector` 的默认 inset 是单机实测值** `.measured1470x956 = (14, 9, 14, 9)`（FullscreenGeometry.swift:46）。换一块屏这个补偿不一定成立，`covering` 会漂。注释已经自认是实测值，留着可以，但值得记一笔。
- **开着全屏应用启动 → 不 hold**：`re-evaluate(trigger: .start)` 时两个「几何外信号」恒为 false，判定必然 false。设计如此（没有边沿记忆），但用户看到的是「壁纸盖在全屏应用上」。
- **菜单「暂停」在已被系统压住时也显示「暂停」**：`isPaused` 读的是 `arbiter.isManuallyPaused`（MenuContentView:42）。锁屏中点它会叠加一个 `manualPause`，解锁后仍然暂停着。`HoldStatus.summary` 已经备好了原因文案，菜单可以区分「继续」与「已被锁屏压住」。
- **转码队列没有暂停/取消**，降帧队列有。一批几十个 MKV 转起来停不掉。
- **自绘 `GlowSlider` 没有任何 accessibility 修饰**：没有 `accessibilityValue`、不是 adjustable，VoiceOver 用户改不了速度和音量。`GlowToggle` 同理缺 on/off 值。按钮类的 identifier 都齐了，滑杆这块是漏的。
- **`SettingsView` 强制 `.preferredColorScheme(.light)`**（:69），无视系统深色外观。
- `TranscodeSection` 的 `sizeText` 在 `body` 求值里 `new ByteCountFormatter()`（TranscodeViewModel:80），每次重绘每行一个对象；配合上面没有 `LazyVStack` 的问题会更明显。
- `SettingsView.applyWindowChrome()` 用 `DispatchQueue.main.asyncAfter(0.5)` 找窗口（:350），时序碰运气。
- `ChoiceGrid` 里 `.accessibilityElement()` 写了两遍（:250、:252），无害但重复。
